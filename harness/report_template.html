Experiment report · Apache Pulsar v4.2.5 · Sonnet 5.5

Does a jQAssistant code graph make a coding agent better?

Mostly not. On seven of eight tasks the agent with a Neo4j graph of the code base did no better than the agent with grep. The graph earned its keep on one question type, ranking classes by how many others depend on them, and only when the prompt told the agent it was there.

The rig

Same agent, same prompts, one difference

Every run starts from a fresh git worktree of the same Pulsar commit. All three setups get the same model, tools, permissions and turn limit. Setups B and B0 additionally reach a read-only Neo4j MCP server holding a jQAssistant scan of eleven Pulsar module jars. Code changes are compiled afterwards in a JDK 21 container, and an Opus model judges each diff blind.

Verdict

Where it shone, where it failed

Shone: counting across the code base

Ranking classes by how many others depend on them is one aggregate query in the graph and guesswork with grep. With the schema hint the agent used the graph and stayed level with the baseline; in the single pilot run it named all ten. Without the hint it wrote clumsier queries and did worst of all.

No difference: everything grep can find

Implementers of an interface, adding a method everywhere, a new config option, renames with distinctive names. Grep gets these in one or two calls, the agent often skipped the graph when it had it, and quality and cost stayed the same.

Failed: the rename grep cannot disambiguate

Renaming Position.getLedgerId() failed in all nine runs. The graph knows which call sites resolve to Position, and the graph runs queried exactly that, yet agents still renamed unrelated and generated protobuf methods. Precise data did not stop imprecise edits.

Is it worth pursuing?

Not as a general data source in this form. The graph is built from compiled jars, so it has no tests, no line-accurate source and no unmerged changes, and it goes stale with every edit. A capable model with grep already closes most of the gap. It may still pay off for questions grep cannot answer at all: dependency cycles, unused public API, layering rules, transitive impact through overrides, or as a check after the agent's edit that every caller of a type was updated. Those were barely tested here and are the next experiment worth running.

Caveats

How far to trust this

  1. Small sample. Three runs per cell. Only B0 on the ranking task stands clearly apart.
  2. Jar-based graph. Released jars of eleven modules: no tests, no source lines, no Maven module relations.
  3. Partial compile check. Main code of three to five modules, built offline in Docker. Callers elsewhere would go unnoticed, equally for every setup.
  4. Circular ground truth. The true answers for T02 and T07 come from the same graph the graph setups query, which favors them.
  5. Blind but limited judge. Opus sees only the task and the diff and cannot search the repository, so its "incomplete" calls are partly guesses. Two judgments failed and are left out.
  6. One flawed prompt. T08 asked for an edit in conf/broker.conf while limiting edits to src/main; several runs of every setup skipped the file.
  7. Delegates count as compiling. Where an interface requires the old name, agents kept a delegating method. That compiles but is not a full rename.
